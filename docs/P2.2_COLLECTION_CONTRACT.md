# Collection Importer Contract v0.3

## Purpose and boundary

P2.2 acquires collection membership (`collection_id -> note_id[]`) as a separate derived data domain. P1 content acquisition and its lifecycle remain frozen. The future importer belongs in `src/xhs_collection_importer/`; it must not be integrated into `SyncRunner` or `src/xhs_ingest/`. P2.1 owns the single copy of each exported note and its media.

```text
P1: XHS note details -> sync.db + data/<note_id>/ (frozen)
P2.1: local COMPLETE notes -> Vault/notes/<note_id>.md + Vault/assets/
P2.2: collection listing and membership -> versioned knowledge snapshot
P2.2 projection: collections.json -> Vault/collections/<collection_id>.md
```

This contract is grounded in `docs/P2.2_COLLECTION_EVIDENCE_REPORT.md` (Phase 0, 2026-09-17). The report observes one authenticated board-list page and one board's SSR first batch plus one API terminal page. It does **not** demonstrate multi-page board listing, a genuinely empty board, or terminal responses for every board. Its explanation for the 43 reported versus 41 observed notes is a hypothesis, not proof that the missing two were deleted.

## 1. Observed sources and authentication

Use the target account's authenticated Playwright persistent profile in a separate run. Do not run alongside P1; concurrent sessions may lock or change the profile. Use DOM navigation and response interception so the site's frontend supplies its own signing headers. The unsigned direct request returned HTTP 406 in Phase 0. Verify `window.__INITIAL_STATE__.user.loggedIn === true` and non-guest account identity before accepting any board list. HTTP 200, a DOM label such as `专辑・0`, or a board page with `温馨提示` is not proof of an empty result; treat login prompts and such warnings as auth failures.

The following requests and shapes were observed for this account; they are not a stable public API guarantee:

| Purpose | Observed browser-triggered request | Observed browser state |
| --- | --- | --- |
| Board listing | `GET https://edith.xiaohongshu.com/api/sns/web/v1/board/user?user_id=...&page=1&num=30&...` | Profile `?tab=fav`, clicked `专辑`; response `code=0`, `success=true`, `data.boards`, `data.board_count` |
| Board membership | `GET https://edith.xiaohongshu.com/api/sns/web/v1/board/note?board_id=...&num=30&cursor=...&...` | `/board/{boardId}` initially exposes `window.__INITIAL_STATE__.board.boardFeedsMap._rawValue[boardId]` |

Validate the response envelope (`HTTP 200`, JSON, `success === true`, `code === 0`), account and board identity, and required typed fields before accepting data. SSR uses `noteId`, `hasMore`, `cursor`; the observed API page uses `note_id`, `has_more`, `cursor` within `data`. Normalize the two shapes explicitly. Absent, null, or malformed completion fields must never be coerced to `false`.

### Evidence limits and future validation

The one-page list (`board_count=2`, two distinct board IDs, `num=30`) and the `coding` member API terminal response are observed. Multi-page board pagination, empty boards, private-board access, and all other failure envelopes remain unverified. Probe those cases before claiming their completion semantics. Do not generalize `board_count` equality to unobserved pagination behavior.

The evidence report itself includes a sample `xsec_token`; this contract does not authorize copying it into importer output, logs, tests, or a Vault. Future evidence must redact such credentials and signed URLs. Phase 0 and the importer are relationship listing only: no note detail navigation or media acquisition.

## 2. Relationship model

* `source_user_id` scopes collection IDs and prevents merging snapshots from different accounts. Derive it from the authenticated account and verify it matches the responses when available.
* `collection_id` is the stable collection identity within that account; the observed two IDs are 24-hex. Validate safe identifiers but do not infer that all future IDs or rename behavior were proven by one observation. `name`, `desc`, `privacy`, and reported count are display metadata.
* Input is one `collection_id` from the validated board list. Output is a set of `(collection_id, note_id)` relationships, with optional observed title. The SSR initial `notes` are the first batch; use its `cursor` only when `hasMore === true`, then intercept board API pages until a validated `data.has_more === false`. Do not issue a first-page API request that silently discards SSR notes.
* Normalize SSR `noteId` and API `note_id` to the same identity. Within a board, retain the first occurrence of each valid note ID, count later occurrences as duplicates, and flag conflicting identities or titles for diagnostics without inventing a second relation. Preserve the same note in different boards (N:M). Sort output collections by `collection_id` and members by `note_id` for deterministic bytes; source order and `position` are not guaranteed and are not persisted as authoritative order.
* Report `raw_items_seen`, `unique_members`, and `duplicate_items` separately. A reported total (`43`) differing from acquired unique members (`41`) is a discrepancy, not evidence of deleted notes or a reason to synthesize missing members. It requires a warning and cannot alone negate a valid terminal signal.
* No published output or diagnostic may contain Cookie, `xsec_token`, token-bearing or signed URLs, request headers (including `x-s` and `x-t`), or raw response bodies. Membership does not require a reusable note-detail credential.

## 3. Output and snapshot consistency

```text
knowledge/
├── current.json                         # atomic pointer to last committed COMPLETE snapshot
├── last_attempt.json                    # optional sanitized failure/partial diagnostics
└── snapshots/<snapshot_id>/
    ├── collections.json
    └── collection_manifest.json
```

`current.json` is the sole authority for a published snapshot. It contains `snapshot_id`, `captured_at`, `collections_hash` (SHA-256 of the exact UTF-8 bytes of that generation's `collections.json`), `status: "COMPLETE"`, and `source_user_id`. Both immutable generation files carry the same ID, account ID, and capture time; the manifest repeats `collections_hash`, status, listing and per-board evidence. A reader resolves `current.json`, then verifies both file identities, statuses, and exact hash before using relationships. Reject missing, mismatched, or unsafe paths and IDs.

Stage a new, unique generation in `knowledge/snapshots/`, write and validate both files, and make them immutable. Only after every board and the listing are proven `COMPLETE`, atomically replace `current.json` with a pointer to that generation. An interruption before pointer replacement leaves the old complete snapshot current; an unreferenced staging generation is never a published result. Do not overwrite or prune the current generation during acquisition. A failed, partial, or unverified attempt records sanitized status and stage-specific errors in `last_attempt.json` (atomic replacement) and leaves `current.json` unchanged. If no previous complete snapshot exists, leave `current.json` absent. Never publish `SUCCESS` for a failed attempt; `COMPLETE` is the sole success status. The old snapshot may become stale; display its original `captured_at` and the latest attempt status separately.

Use fixed JSON key order, stable collection/member sorting, and encoding. For identical observed relationships, the relationship body is byte-identical after excluding capture metadata; `snapshot_id` and timestamps may change. Counts reconcile to unique relationships. An incomplete attempt can be retained only as non-authoritative, sanitized diagnostics and must not replace the current mapping.

### Committed snapshot (illustrative shape)

```json
{
  "snapshot_id": "capture-20260917-001",
  "captured_at": "2026-09-17T13:30:00Z",
  "source_user_id": "observed-user-id",
  "collections_hash": "sha256-of-exact-collections-json-bytes",
  "status": "COMPLETE"

```

The example above is `current.json`. Each generation's `collections.json` has `snapshot_id`, `captured_at`, `source_user_id`, and `collections: [{collection_id, name, total_reported, members: [{note_id, title}]}]`. Its manifest includes at least:

The example represents a hypothetical one-board account, not the observed two-board account. A real `COMPLETE` manifest must list **every** validated board and its terminal proof. Errors identify stage, board ID where applicable, and category, without raw payloads or credentials.

For Phase 1 diagnostics, use separate axes: `board_listing_status` records catalog completeness, `member_relationship_status: "NOT_STARTED"` says member acquisition has not begun, and `publication_status: "NOT_PUBLISHED"` says there is no committed relationship snapshot. `NOT_STARTED` and `NOT_PUBLISHED` describe workflow stages, not additional completion-proof values. A Phase 1 `last_attempt.json` may retain overall `status: "PARTIAL"` under the four-value attempt vocabulary, but consumers must not interpret it as a partial board listing; inspect `board_listing_status` directly.

## 4. Completion proof

1. **Board listing:** `board_count` is a server-reported count, not a general pagination terminal signal. For the **observed single-page case only**, an authenticated `code=0/success=true` page 1 with a valid nonnegative `board_count <= requested num`, that many distinct valid IDs, and matching owner can be marked `COMPLETE` with proof `AUTHENTICATED_SINGLE_PAGE_COUNT_MATCH`. The observed `2 of 2` satisfies this narrow condition. If `board_count > num`, IDs/count disagree, a page is malformed, or further pages are needed, listing remains `PARTIAL` or `UNVERIFIED` until pagination and terminal semantics are independently evidenced. Do not equate an empty later page, limit, or stall with completion. `boards: []` plus `board_count: 0` in an authenticated successful response would be a candidate empty-list proof, but this case was not observed and must be validated before use; `专辑・0` alone is an auth-risk symptom, never proof.
2. **Each board's members:** validate the SSR first batch and its `hasMore`/`cursor`; merge it with intercepted API pages tied to that `collection_id`. The observed `coding` board supplied 37 SSR items and four API items with explicit `data.has_more === false`. Only the exact boolean `false` in a validated server response (or a separately evidenced terminal equivalent) proves API termination. An SSR `hasMore === false` without API terminal evidence remains `UNVERIFIED` until that condition is validated. Missing/null fields, repeated cursor, duplicate-only page, timeout, or interruption are not terminal proof. A truly empty board is **not** established by the report: require an authenticated owner, valid empty SSR/response and explicit terminal evidence; until observed, status is `UNVERIFIED`.
3. Keep listing status separate from each board's status. A failed board must not erase verified members of other boards or imply that no other boards exist. Record the last validated page and continuation cursor only if semantics were verified; never put sensitive tokens in public output. The observed second board has no reported terminal evidence in Phase 0, so the report alone cannot justify an account-wide `COMPLETE` snapshot.
4. `total_relations` counts distinct `(collection_id, note_id)` pairs; `distinct_notes` counts unique note IDs across collections. Reported server totals are separate observations and do not replace these computed counts.

Local P1 `COMPLETE` notes absent from the acquired mapping are `unmatched_local_notes`, not proven unclassified remote favorites. P1 remote coverage remains `UNPROVEN` even when P2.2 board enumeration is complete.

## 5. Vault projection boundary

```text
Vault/
├── notes/<note_id>.md
├── assets/
└── collections/<collection_id>.md
```

Future projection only: each collection index has `collection_id` and current human-readable `title` in frontmatter, and links to the single note at `../notes/<note_id>.md`. The ID-based filename survives a rename and avoids same-name collisions. Validate safe IDs; escape display titles. Link only notes present in the exported Vault. Track ownership and remove only importer-owned stale indexes, never user files or P2.1-managed notes/assets. Do not project an inconsistent or incomplete snapshot. **Vault projection is outside this importer task.**

## 6. Strict P1 and acquisition boundary

1. Do not mutate P1 `sync.db`, change its schema, or write under `data/`. No P1 status read is required for relation acquisition.
2. Allowed: authenticated Playwright session, board page navigation, browser response interception, and relation extraction. Do not invoke P1 synchronization or Collector, fetch detail pages, or navigate to individual notes. No implicit retry of P1 failures.
3. Do not intentionally request, download, or persist image/video assets. Incidental browser page resource loading outside the importer's control is not media acquisition; block media resources where practical.
4. Keep the `knowledge/` output outside `data/`, `.xhs-state/`, and the Vault. Reject overlapping or symlink-resolved unsafe paths before writing.
5. Do not copy note files into collection directories. P2.1 remains the sole owner of `Vault/notes/` and `Vault/assets/`.

## 7. Acceptance gates before importer MVP

* Phase 0 evidence authorizes only the observed single-page board list and SSR-plus-API member path. Multi-page list, empty board, and other unsupported shapes fail closed until independently observed.
* Tests distinguish `UNVERIFIED`, `PARTIAL`, `FAILED`, and `COMPLETE`, including auth showing a false empty list, missing `has_more`, SSR/API overlap, repeated cursor, duplicate IDs, interruption, errors, and a board rename.
* Only an immutable complete generation can become `current.json`. On crash or failed acquisition the previous current snapshot stays readable; hash or ID mismatch is rejected, and no `COMPLETE` or `SUCCESS` is emitted for that attempt.
* Repeated capture of unchanged relationships is deterministic apart from capture metadata. Counts reconcile to unique `(collection_id, note_id)` pairs and N:M membership is preserved.
* Before and after a real run, `sync.db` and `data/` file contents and listing hashes remain identical. No detail page or media download is initiated.
