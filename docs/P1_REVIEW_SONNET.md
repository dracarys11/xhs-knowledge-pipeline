## Verdict

**条件批准（Conditional Approve）。**

这是一份高质量、思考严密且工程感极强的增量同步设计方案。方案基于 SQLite 构建按 note 粒度的状态机与事务提交机制，彻底摒弃了内存态的脆弱假设，并且将 Fail-Closed 与幂等性原则贯彻到每个状态跃迁中，精准命中了 `P0_TO_P1_REVIEW` 提出的 7 项核心要求。

**但是，若按当前文档直接进入编码，在面对真实 1000+ 收藏同步场景时，会遭遇 4 个严重的架构与运行时隐患**（包括两阶段阻塞陷阱、详情采集风控、URL 过期与 raw.json 不可变死锁、以及长周期浏览器内存泄漏）。方案必须在实现前吸收这些关键修正，以确保大规模批量同步真正具备生产级健壮性。

## Confirmed Strengths

1. **状态机与存储介质选型极其务实**
   放弃复杂的外部消息队列或多表关系设计，选择标准库 `sqlite3` + WAL 模式，以 `note_id` 为主键，每次状态跃迁与媒体完成单事务写穿。这在单机本地 CLI 架构下提供了最低的复杂度与最高的崩溃一致性。
2. **`FETCHING` 瞬态崩溃自愈模型设计精妙**
   明确定义 `FETCHING` 仅作为崩溃痕迹存在，绝非合法静止态。启动时统一执行 `UPDATE notes SET status='PENDING' WHERE status='FETCHING'`，既能消除悬空状态，又通过同时递增 attempt 计数防止崩溃死循环。
3. **清醒承认滚动分页无法注入游标的物理现实**
   没有为了“形式上的断点”去设计伪 cursor API 或强行逆向加密签名（x-s）。正视浏览器驱动的现实，选择“枚举断点 = 从头重扫 + SQLite upsert 幂等吸纳”，取舍极其诚实且工程成本最低。
4. **彻底修复 P0 的完成判定缺陷，建立停滞 Fail-Closed 机制**
   废除无意义的 `FOUND_N_ITEMS`，唯一合法完成证据绑定服务端 `has_more == false`。引入“连续 5 次滚动无新增且无服务端终止证据即异常中止”的防御，直接补死了外部开源项目（如 ONEMULE）将滚动停止误当成全量完成的经典漏洞。
5. **轻量化 `media_state` JSON 列取舍合理**
   在千级 note 规模下，不建独立媒体表是正确的工程节制。单篇笔记媒体数量一般不超过数十个，JSON 列完全能胜任按文件级别的重试与 skip-if-verified 校验，避免了冗余的 SQL JOIN 复杂度。

## Critical Risks (必须在实现前修改的问题)

### 1. “全量枚举完成才开始 Ingest”的两阶段阻塞陷阱（1000+ 收藏的核心致命伤）

- **问题定位**: §1 链路图与 §8 `sync.py` 逻辑将流程划分为严格的两阶段：`favorites 全量枚举 (直到 has_more=false) -> 逐篇 ingest`。
- **失效场景**: 用户有 1000 条收藏，在浏览器中滚动需要 40–50 次交互。假设在滚动到第 30 次（已发现 600 篇）时，因网络抖动、偶发风控滑块或 DOM 渲染卡顿触发了停滞异常（`UnknownAcquisitionError`），整机抛出 exit code 2 中止。
  **由于 Phase 1 未正常结束，Phase 2 根本不会启动！** 用户已成功落库的 600 篇 `PENDING` 笔记被完全冻结。当用户重新执行 `sync` 时，系统又从顶部重新开始滚动，并在同一批次附近再次受阻退出——系统陷入死循环，已发现的笔记永远无法被消费落盘。
- **必须修改**:
  1. `sync.py` 必须解耦“枚举”与“消费”。启动时若检测到 SQLite 中已有遗留的 `PENDING` / `MEDIA_PARTIAL` 记录，**应优先处理或支持配置处理已有队列**。
  2. 若枚举过程非致命中断（如网络抖动或滚动停滞，而非全局 `AUTH_REQUIRED`），系统记录警告日志后，**应降级进入消费当前已捕获的 PENDING 队列**，而不是全流程暴毙。

---

### 2. 详情采集阶段（Phase 2）缺失请求节流与抖动（风控拦截必然发生）

- **问题定位**: §5.2 为 Phase 1 滚动枚举细心设计了 1.5–3.0s 的随机抖动延迟，但在 Phase 2 `fetch_note` 消费循环中，方案未定义任何强制延迟策略。
- **失效场景**: P0 smoke test 仅验证了单篇笔记的提取。当 Phase 2 连续处理 1000 篇笔记时，如果循环以机器极限速度（上一个刚完立即请求下一个）连续向 `https://www.xiaohongshu.com/explore/<id>` 发起导航，小红书前端风控在 20–30 次连续请求内必定弹窗验证码（`RISK_CONTROLLED`）或触发 429。这会导致单次运行被强行掐断，1000 篇根本无法自动化推进。
- **必须修改**:
  1. 在 `sync.py` 的逐 note 消费循环中，强制加入 note 间的随机休眠（例如默认 `random.uniform(2.0, 4.5)` 秒）。
  2. 暴露 `--delay` CLI 参数允许用户根据自身网络和账号状态微调。

---

### 3. `raw.json` “不可重写” 规则与 403 签名过期刷新 URL 的逻辑死锁

- **问题定位**: 
  - §6 明确规定：“`raw.json` 一旦存在且 `DETAIL_SUCCESS` 则不重写”。
  - §7.1 又规定：“若媒体下载命中 HTTP 403（CDN 签名过期）... 下次运行重新走 detail 获取新 URL”。
- **失效场景**: 小红书视频与部分高分辨率图片 CDN 链接带有 TTL 签名（URL 包含 `sign=...&t=...`，通常数小时内失效）。若一篇笔记处于 `MEDIA_PARTIAL`，第二天重试时媒体必定 403。按 §7.1 重新走 `fetch_note` 获取了包含最新签名的新 payload，但由于 §6 规定“raw.json 不重写”，导致新数据无法覆盖落盘！后续媒体下载流程从旧 `raw.json` 重新 normalize，提取出来的仍然是过期失效的旧 URL，再次 403，最终不可逆地进入 `FINAL_FAILED`。
- **必须修改**:
  - 修正 §6 规则：当 note 因媒体失效重刷 detail 或处于非 `COMPLETE` 状态重新 fetch 时，**新获取的原始数据必须以原子重命名方式覆盖现有的 `raw.json`**。

---

### 4. 单一 Playwright `Page` 连续导航 1000 次将导致渲染器内存耗尽 (OOM)

- **问题定位**: §8 collector.py 变更 ④ 提出“运行级浏览器 context 复用，sync 期间单 context，退出时关闭”。
- **失效场景**: 小红书是重度 SPA 页面，包含大量的 Vue 响应式状态、视频解码上下文、Pinia/Vuex Store 以及埋点脚本。在同一个 Playwright `Page` 上连续执行数百次全页路由跳转，Chromium Renderer 进程内存会持续线性增长直至超标（在 macOS 上易突破 3–4GB），最终抛出 `TargetClosedError: Page crashed`。
- **必须修改**:
  - 保持 `BrowserContext` 长期存活（以维系 Cookie 与持久会话），但**对具体的 `Page` 实行生命周期轮换**：每处理 25–30 篇笔记，或者在捕获到页面异常后，显式 `page.close()` 并通过 `context.new_page()` 重置渲染树。

## Recommended Adjustments (应该注意的工程细节)

### 1. `.complete` 标记缺失应细化为“自动修补”而非直接“推倒重采”

- **背景**: §6 降级守卫提出“COMPLETE 但 .complete 或 canonical.json 丢失 -> 降级 PENDING 重新全量采集”。
- **隐患**: 存在一个微小的崩溃窗口：SQLite 事务成功将状态标为 `COMPLETE`，但随后写入 `.complete` 标记前进程异常杀死。此时磁盘上的 `raw.json`、`canonical.json` 及所有媒体文件（含 SHA256）100% 完好无损。下次启动直接判为 `PENDING` 并重新下载，是巨大的无意义重跑。
- **建议**: 降级守卫拆分为两步：
  1. 若关键内容（`canonical.json` 或媒体文件）缺失或校验不通过，降级 `PENDING`；
  2. 若媒体与元数据全部校验通过，仅缺失 `.complete` 标记文件，直接补写 `.complete` 并保持 `COMPLETE`，避免惩罚性重采。

---

### 2. 增加对 SIGINT (Ctrl+C) 的平滑处理保证

- **背景**: 1000 篇采集耗时预计在 1–2 小时之间，用户中途手动中断（Ctrl+C）是确定性高频事件。
- **建议**: `sync.py` 必须注册信号捕获（或 `try...except KeyboardInterrupt`）：
  - 停止分发下一个任务；
  - 等待当前正在原子写入的单个媒体或单个元数据完成；
  - 若处于 `FETCHING`，将其干净置回 `PENDING`；
  - 关闭浏览器上下文后退出，确保终端输出可理解的保存提示（如：“同步已被用户暂停，当前进度已完整保存至 SQLite，可随时再次运行恢复”）。

---

### 3. 滚动停滞检测（Stall Detection）必须排除“在途网络请求”

- **背景**: §5.2 提出“连续 5 次滚动无新增条目且无服务端终止证据 -> 异常中止”。
- **建议**: 在网络较慢或小红书服务器响应出现 2–3 秒延迟时，可能连续 2 次滚动期间同一批请求还在传输中。停滞计数器的增加必须附加前提：**当前无在途未返回的 `/api/sns/web/v2/note/collect/page` 请求**，避免由于单纯的网络等待误判为页面停滞。

---

### 4. `sync_meta` 初始化显式默认值

- **建议**: `state.py` 数据库首次创建时，应显式插入 `last_enumeration_status = 'NEVER_RUN'` 等默认键值对，避免在业务代码中散落大量的 `if meta is None` 边界分支，使状态机查询更确定。

---

## Not a Problem (无需修改的设计取舍)

- **不引入媒体独立关系表**: 1000 note 对应媒体总数在万级以内，`notes.media_state` JSON 文本存储足以支持断点与校验，没有跨 note 统计媒体的需求，保持单表是最优解。
- **不保留枚举 cursor 用于断点恢复**: 页面由前端内部状态滚动驱动，不支持反向传参，方案选择重头滚动并通过 SQLite upsert 吸收是清醒现实的抉择。
- **不做并发抓取与多线程下载**: 批量增量同步的生命线是“可恢复性、正确性与低风控风险”，而不是极致带宽吞吐。顺序抓取配合抖动是反爬环境下的最稳妥模式。
- **`PageResult.raw` 完整捕获所有拦截数据**: 保留整个 response payload 虽略增体积，但对后期接口变更排错和诊断具有不可替代的价值。
- **`--retry-failed` 作为终极失败的显式人工重置开关**: `FINAL_FAILED` 不自动重试，把决策权交还给操作者，避免对永久失效内容（如违规/作者删除）做无意义的重复冲击。
